## 0. 一行で言うと

各「まち」について、そこがこれまでどういうまちで、いまどういうまちなのかをストーリー立てて整理し、それを歩ける地図に翻訳して、1まち=1URLで蓄積する個人プロジェクト。マップを見てまち歩きをすると、成り立ちから現在までの「まちの流れ」が読め、そのまちへの理解が深まる——これがマップの一番の目的。名前の由来もここ: 時間(Time)を歩く(Walk)。

## 1. 設計思想(実装より先に読む)

### 1-1. これは分析プロジェクトではなく、編集・翻訳プロジェクト

まちの特徴に関する文献・情報はネット上に十分すぎるほどある。本筋は「データを掘って特徴を発見する」ことではなく、**「文献からまちの特徴を整理し、それをマップで可視化する」**こと。

マップの固有の仕事は、「文献としては知られているが、地図としては存在しない」ギャップを埋めること。「銀座は路地とギャラリーのまち」と文章で読んで知っていることと、どの街区の裏にどう路地が張り付いているかを地図で見て現地に足を運べることの間には大きなギャップがある。

このプロジェクトの独自ポジション: 「まちの特色がまとめてあり、それを読んでから、具体的にどのエリアを歩けばそれが見られるのかまで示す」。まち歩きガイドはスポットを列挙するが空間構造を示さない。GIS分析は構造を示すが物語を語らない。両方をつなぐものは(知る限り)存在しない。

### 1-2. ストーリーが設計図

最重要の原則: 「そこがこれまでどういうまちで、いまどういうまちなのか」をストーリー立てて説明することがすべての中心。レイヤ・データ・情報系統(§2-2)はこのストーリーに奉仕する手段であり、逆ではない。

まちの成り立ちの物語が、マップの設計図そのもの。例: 「明治の煉瓦街がグリッドを作り、震災と戦後がその裏に路地を残し、高度成長期に画廊が集積した」——この物語の各文が、それぞれマップのレイヤに対応する。レイヤは物語の挿絵。

したがって制作順序は: 文献を読む → ストーリーを組む → ストーリーを語るのに必要なレイヤを選ぶ → 翻訳する。

### 1-3. GISの役割 = 裏付けと解像度

GIS/データ分析はコアから降りるが、無くならない。役割は文献の主張に座標と解像度を与えること。文献「銀座はギャラリーのまち」→ データ「具体的にどこに、どの密度で、どの通り沿いに」。

ときにデータが文献を修正する(「路地が多い」が実は特定の丁目に極端に偏っている等)。その場合は修正した姿を描く。

「らしさは差分」(他のまちとの比較で特徴を裏付ける)は、効くときだけ使う薬味。必須工程ではない。

### 1-4. 雰囲気優先・推進力優先

厳密な悉皆調査ではなく、まちの雰囲気・流れがつかめることを優先。抽出条件は緩めでよい(例: 路地はalleyに限定せず細い歩行者空間全般を「歩く空間の網」として見せる。網の濃淡そのものが肌理)。

公開基準は緩め: テンプレートに沿って1本完成したら公開してよい。 完全性より推進力。積極的にスコープを絞る。

### 1-5. 位置精度ポリシー

歴史的情報(「戦前の花街があった一角」等)は正確なポリゴンが存在しないことが多い。「およそこの辺り」の緩い表現(半透明の円・エリア塗り)で示す割り切りを採用する。

ただし、確度の低い位置は視覚的に区別する(例: 破線・半透明・「推定」ラベル)こと。正確な現況データ(OSM由来等)と同じ見た目で描かない。誤りを事実として地図に固定しないための最低限の作法。

出典は [データと手法] セクションに必ず記載。

### 1-6. 掲載倫理の一線

遊郭跡・旧同和地区に隣接する話題など、現在そこに住む人がいる場所のセンシティブな歴史を扱う際は、既刊の書籍・自治体資料・確立した郷土史等で公に語られている範囲に限って掲載する。個人の推測やネット上の噂レベルの情報は地図化しない。

迷ったら載せない。このプロジェクトはまちへの理解と愛着を深めるためのものであり、レッテル貼りの道具にしないこと。

## 2. 制作ワークフロー(1まちの作り方)

### 2-1. 工程

Step 1: 取材メモ作成(人力+AI併用)
        - そのまちについての文献・記事・自治体資料・都市史を読む
        - 「これまでどういうまちで、いまどういうまちか」のストーリー骨子を書く
        - ストーリーを支える「特徴の主張」をリスト化し、各主張に
          「地図化可能か? どのデータで? 位置の確度は? どの情報系統(§2-2)か?」を付記
        → notes/<town>.md として残す(リポジトリに含めてよい)

Step 2: レイヤ選定
        - ストーリーを語るのに必要な 3レイヤ以内を、§2-2 のメニューを参考に選ぶ
        - 選定基準: ①まちの流れ(成り立ち→現在)が読めるか
                    ②歩いて確かめられるか
                    ③空間構造として見えるか

Step 3: データ整備・地図化
        - OSM(Overpass)、自治体オープンデータ、手動プロット等で各レイヤを作る
        - 歴史レイヤは §1-5・§1-6 のポリシーに従う

Step 4: ページ組み立て
        - マップ + 解説を1ページに統合(§3)

Step 5: 公開(GitHub Pages)、index.html の一覧に追加

### 2-2. 情報系統メニュー(編集の視点の参考)

レイヤ選定の際の引き出し。全部やるのではなく、ストーリーが要求する系統だけを選ぶ。 「このまちの流れを語るには、どの系統が必要か?」と問うための道具。

| # | 系統 | 内容・例 | 備考 |
|---|------|---------|------|
| ① | 痕跡・跡地 (Traces) | 消えたが構造や気配が残るもの。旧遊郭・花街跡、暗渠(旧河川)、旧街道、闇市跡→現在の飲み屋街、工場跡→マンション群、旧軍施設 | 推定エリア表現(§1-5)の主戦場。暗渠は特に強い——線として現在の道路に残り、歩くと不自然なカーブの理由がわかる。§1-6 の倫理ポリシー適用対象 |
| ② | 骨格 (Skeleton) | 街路・街区パターンの由来。グリッド(銀座の煉瓦街)、城下町の折れ曲がり、耕地割がそのまま住宅地区画になった跡 | 年代別空中写真と最も相性が良い |
| ③ | 集積 (Clusters) | 現在の「らしさ」の主役。ギャラリー、古書店、問屋街、専門料理店 | OSM+手動プロットの現況レイヤ |
| ④ | 境界と分断 (Edges) | 旧町名の境界、鉄道による分断、崖線。「この線を越えると雰囲気が変わる」の正体 | |
| ⑤ | 地形 (Terrain) | 坂、谷、埋立地、微高地 | 地理院の陰影起伏図タイルをベースマップ候補に追加可。東京は「谷=旧花街・飲み屋街、台地=屋敷町」の対応が強く①②と連動 |
| ⑥ | 地名の化石 (Toponyms) | 旧町名、交差点名・バス停名にだけ残る失われた地名 | 点レイヤとして軽い。まち歩きの「発見」体験と好相性 |
| ⑦ | 定点 (Anchors) | 神社仏閣・老舗。街路より古いことが多く、「まちが動いても動かなかった点」として時間軸の基準になる | |
| ⑧ | 視点場 (Viewpoints) | 「この交差点に立って南を見ると、震災復興道路の幅の違いが体感できる」等、まちの構造が身体で見える立ち位置 | TimeWalkならではの発明候補。「歩ける形への翻訳」を最も文字通りに実現するレイヤ |

## 3. 成果物の形(1まち = 1URL)

各まちは1ページで完結。街歩き前提なので「現地で見る地図」+「読む解説」の二部構成。マップより上に長文を置かない(現地ではマップしか見ない)。

```
[まち名 + 一行キャッチ]
  ↓
[マップ本体]          ← ページの主役。ファーストビューでほぼ全画面
  ↓
[このまちの特色]      ← 文献整理の成果。特徴の主張を簡潔に。
                        「これを読んでから歩くと何が見えるか」を示す
  ↓
[まちの流れ(成り立ち→現在)]
                      ← 都市史ナラティブ。マップのレイヤと明示的に接続
                        (「なぜ路地がこの形なのか」に歴史が答える構図)
  ↓
[データと手法]        ← 出典(文献・データ両方)、抽出条件、位置確度の注記、
                        GitHubリンク
```

1ファイル完結(folium出力HTMLの末尾に解説セクションの`<div>`をHTML追記する方式)を基本とする。モバイルで軽快。

## 4. マップ仕様(軽さが最優先の制約)

foliumはデータを全部HTMLに埋め込むため、埋め込むGeoJSONを削る工夫がすべて。

### ベースマップ(切替式)

| レイヤ | タイル | 用途 |
|--------|--------|------|
| デフォルト | CartoDB positron(淡色) | 現地での実用。軽く、自作レイヤが映える |
| 航空写真(現在) | 地理院 seamlessphoto | まちの肌理を見る |
| 航空写真(年代別) | 地理院 年代別空中写真 | まちの流れを読む装置。成り立ちセクションと連動 |
| (任意)陰影起伏 | 地理院 陰影起伏図 | 地形系統(§2-2 ⑤)を使うまちのみ |

```python
# 地理院タイル(無償・出典表記のみ)。attr="国土地理院" を必ず付ける
folium.TileLayer(
    tiles="https://cyberjapandata.gsi.go.jp/xyz/seamlessphoto/{z}/{x}/{y}.jpg",
    attr="国土地理院", name="航空写真(現在)"
).add_to(m)
# 年代別の例: 1945-50年(米軍撮影) → ort_USA10/{z}/{x}/{y}.png
#             1961-69年           → ort_old10/{z}/{x}/{y}.png
#             1974-78年           → gazo1/{z}/{x}/{y}.jpg
# ※ タイルIDと提供範囲は地理院タイル一覧で実装時に要確認。対象まちが
#   カバー範囲内かも確認すること(東京都心部は概ね全年代カバー)。
```

年代別写真をレイヤ切替すると「戦後焼け跡 → 高度成長期 → 現在」を同じ画面で行き来できる。「まちの流れを読む」というTimeWalkの目的を、ベースマップ自体が担う。

デフォルトを淡色にする理由: ①現地で歩きながらの通信量(写真タイルは重い)、②航空写真の上ではベクタレイヤが沈む。

航空写真上でも読めるよう、自作レイヤは白フチ付きの太線・高彩度色を基本とする。

### 必須仕様

- モバイルファースト。 現地で片手で使える前提。
- 現在地表示: folium.plugins.LocateControl、keepCurrentZoomLevel=True。
- 主題レイヤは最大3つ + 切替UI(folium.LayerControl)。全部載せは重く、現地で読めない。
- 点は CircleMarker(素のMarkerは避ける。アイコン画像リクエストが飛ばず軽い)。数百超なら FastMarkerCluster。
- ポップアップは「名前+一言」まで。 詳細は下部の解説へ送る。
- 推定位置のレイヤは破線・半透明で描き分ける(§1-5)。

### サイズ目標

HTML単体で 2MB以下、できれば 1MB以下。 超えたら: ①bboxを狭く(まちは概ね1km四方)、②gdf.geometry.simplify(0.00001)程度の簡略化、③レイヤ削減、の順で削る。

## 6. 共通資産の考え方(重要な整理)

共通資産は2種類あり、どちらも「見せるためのレイヤ」ではない。表示するレイヤは常にそのまちのストーリーに従って選ばれる(=すべて固有)。

**共通の問いのセット(取材メモのフレーム)**: どのまちにも投げる問い。
- このまちの骨格(街路・街区)はいつ・何によってできたか?
- 何が集積しているか? なぜそこに?
- 成り立ちの痕跡は現在のどこに残っているか?

(§2-2 の情報系統メニューが、この問いの引き出しになる)

**共通の道具箱 map_toolkit.py(コード資産)**: Overpass取得(キャッシュ付き)、「歩く空間の網」抽出、ベースマップのセットアップ(淡色/航空写真/年代別/陰影起伏)、LocateControl等の定型、推定位置の描画スタイル、サイズ計測。同じ道具で測るから、まち同士の比較(「らしさは差分」)が必要なときに成立する。

まちごとのビルドスクリプトは、道具箱を呼び出してストーリーに必要なレイヤだけを組み立てる薄いスクリプトにする。これにより新しいまちの追加コストが下がり、蓄積が続く(3本目で止まらない)。

## 7. コーディング規約(必ず守ること)

このプロジェクトのオーナーが既存プロジェクトで確立している流儀。公開リポジトリなので特に厳守。

### パス・公開

- 公開ファイル・README・コード内に個人情報を含めない。 特に Windows アカウント名を含む絶対パス(`C:\Users\<name>\...` 等)を残さないこと。
- スクリプト内のパスは相対パスで書く: `BASE_DIR = os.path.dirname(os.path.abspath(__file__))` を起点にする。絶対パスをハードコードしない。
- .gitignore で除外: 生データ、キャッシュファイル(`_overpass_*_cache.json` 等)、デバッグ用スクリプト、`data/`。

### Overpass API

- `requests.post()` に User-Agent ヘッダー必須(省略すると 406 エラー。エラーメッセージから原因を判断しにくい)。
- 開発中はキャッシュ: 結果を `_overpass_<town>_cache.json` に保存し、`USE_CACHE = True` を基本にする。

### 出典・ライセンス

- OSMデータ使用時は `© OpenStreetMap contributors` を、地理院タイル使用時は `国土地理院` をマップ上の attribution に表示。
- 文献由来の情報は [データと手法] セクションに出典を列挙。

### 実行環境

- Python 3.11。 主要ライブラリ: pandas, geopandas, folium, requests。
- オーナーはローカルの Windows 環境で実行・検証する。スクリプトはネットワークアクセス前提で書いてよいが、生成される最終HTMLは静的単体で動くこと。

### スタイル

- コメント・出力メッセージは日本語で可。
- コンソールに件数レポート(何をいくつ拾ったか)を出すと検証が速い。

### 最初の1本を銀座にする理由

文献が豊富(煉瓦街・震災復興・画廊集積の物語が確立している)、路地×グリッドの対比が視覚的に強い、年代別航空写真のカバー範囲内。編集翻訳型テンプレートの型を確かめる題材として最適。
